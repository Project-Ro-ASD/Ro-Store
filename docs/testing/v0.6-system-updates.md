# Ro-Store v0.6 — System Updates: single-pass Fedora 44 QA

Status: **draft, not ready for release**. This test checks only non-mutating
operations and explicitly confirmed standalone RPM downloads.

## Build and launch

From the Ro-Store checkout (branch `feature/system-updates-v0.6`):

```bash
git pull --ff-only origin feature/system-updates-v0.6 &&
cmake -S . -B /tmp/ro-store-v060-build -DCMAKE_BUILD_TYPE=Debug &&
cmake --build /tmp/ro-store-v060-build --parallel 4 &&
/tmp/ro-store-v060-build/ro-store
```

Do not use a final bare `ro-store` command after a failed build; it can
accidentally run an older binary.

## Grouped checklist

1. Open **Sistem Güncellemeleri** and refresh. All installed Fedora RPMs
   with enabled-repository updates should appear, including kernel candidates.
   Installed and candidate versions may load separately.
2. Select `7zip` and `assimp`. Verify selected size, package count,
   `Seçilenlerin planını incele`, and the collapsible dependency preview.
   `Tümünü seç` should preview one full-system goal, not trigger installation.
   Inspect removals and kernel changes in the DNF5 plan.
3. In **Güncelleme indirme önbelleği** check the selected cache summary:
   already verified vs missing RPMs. The download-only QA path permits at
   most **12 selected packages** and has a **50 MiB estimated RPM-size**
   UI limit; unknown-size packages are excluded from this test.
   These bounds are *not* a guaranteed network quota, because repository
   metadata and other traffic are not included.
4. With the already cached `7zip` and `assimp` selected, run the preview,
   click `Seçilenleri indir`, and approve. Expect `CACHE HIT` and no
   newly downloaded RPMs.
5. For a genuinely new small RPM, download only after reviewing its size.
   Check the live status line, per-file progress bar, staged byte count,
   elapsed time, and **Günlüğü göster / gizle**. The resulting RPM should
   be checked for exact NEVRA and signature before entering the cache.
6. Try cancelling a standalone RPM download before completion. Its incomplete
   RPM must not appear as verified; previously verified RPMs must remain.
   **Never test cancellation of an actual RPM transaction.**
7. Use **Fedora çevrimdışı güncelleme durumu → Durumu denetle**.
   This is `dnf5 offline status` and is read-only.
8. Verify resizing (400×500, 600×500, 1000×650), full-page scroll,
   independent RPM-list scroll, RTL-free Turkish labels and keyboard focus.
   `Temizle` must request confirmation and never touch system DNF caches.

## Release blockers (must not be marked complete based on QA above)

- Single DNF5 daemon **complete-system** goal for the requested package set,
  including conflicts, removals, dependencies and exact download totals.
- Reuse of validated staged RPMs within the solver-approved transaction; do
  not assume the existing standalone download cache is automatically honored.
- Shared transaction mutex with current install/remove/upgrade queue and
  persisted unknown-outcome recovery journal.
- Kernel/critical RPM offline application and a user-confirmed reboot policy.
  Running RPM mutations must never be forcibly killed.
- Fedora 44 testing for interrupted network, process cancellation, disk-full,
  concurrent operations and interrupted daemon communication.
- GitHub Actions RPM x86_64/aarch64 success and explicit release approval.

Until these safeguards are implemented and tested, **do not add a button
that executes an RPM system upgrade or reboots the machine.**


## New in the offline system-update integration (not yet release-approved)

The **DNF5 tek işlemli çevrimdışı sistem güncellemesi** panel creates a
single DNF5daemon Goal for every selected RPM (and its dependencies), displays
the resolved transaction with removals and estimated transfer size, and keeps
the goal locked against ordinary Ro-Store install/remove operations.

**First QA pass — do NOT execute the offline preparation yet:**
1. Build and open the updated app.
2. In Sistem Güncellemeleri, select 7zip and assimp, click
   **Tek işlem planını çözümle**.
3. Expect a plan with package/dependency/removal information, total download
   estimate, and `SYSTEM UPDATE SINGLE DNF5 GOAL RESOLVED` log.
4. Click **Planı bırak**, change the selection, resolve again. Make sure
   the second plan does not include remnants of the earlier goal.
5. Check that selection/refresh during resolution discards stale approval.
6. Check 400x500, 600x500 and 1000x650 scrolling and button layout.
7. Do not click **Çevrimdışı güncellemeyi hazırla** in this first pass.

**Before any genuine staging test (separate explicit operator decision):**
- Make a verified backup and ensure stable power and enough disk space.
- Verify the complete resolved action list, especially removals, kernel,
  NVIDIA modules, protected packages, downgrade/conflict operations.
- Confirm existing offline DNF5 transaction state is clear. Never overwrite
  another tool's staged offline transaction.
- Be aware DNF5daemon uses its own transaction/package cache. Ro-Store's
  standalone `~/.cache/ro-store/system-updates/rpms` RPMs are NOT guaranteed
  to be reused during this path. The displayed estimate is not a hard data cap.
- Preparing is a privileged DNF5daemon action, and must occur only after
  user approval. It must not reboot automatically.
- A durable journal `pending-offline-system-upgrade.json` in Ro-Store
  AppLocalDataLocation blocks new app transactions after an uncertain result.
  A reboot and a separate recovery check are required before explicitly
  acknowledging it; this does not prove success. Consult `dnf5 offline log`
  and `dnf5 history` for the actual outcome.
- Never forcibly stop DNF5daemon during RPM mutations. DNF5 Goal.cancel
  is requested only by explicit action, and a successful request is not proof
  the operation has finished.
- Final release requires live Fedora preparation/reboot/recovery tests and
  x86_64/aarch64 CI. **Keep PR #16 draft until then.**

### Offline preparation action

Once the plan has been verified and the operator separately agrees, the
controller uses DNF5daemon `org.rpm.dnf.v0.Goal::do_transaction` with
`offline=true` and `downloadonly=false`. Despite `downloadonly=false`,
the documented `offline=true` mode prepares an offline transaction to run
after reboot; it is not an immediate RPM mutation. The application does
not initiate `dnf5 offline reboot` automatically. After DNF5 confirms the
staged transaction, the application presents a **separate** reboot button and
an additional Yes/No confirmation. Clicking it explicitly starts
`pkexec /usr/bin/dnf5 -y offline reboot`; a graphical administrator
authentication may be required. This command can reboot immediately, and must
never be called by CI or in the read-only QA pass. A documented terminal
fallback is `sudo dnf5 offline reboot`, subject to the same precautions.
After reboot, do not clear the recovery journal without inspecting
`dnf5 offline log` and `dnf5 history`.

### Explicitly discard a staged offline transaction

After a successful stage, Ro-Store offers **Hazırlanmış güncellemeyi iptal et**,
requiring another Yes/No confirmation. This calls the DNF5daemon
`org.rpm.dnf.v0.Offline.clean` API, which can delete the offline transaction
and DNF's own downloaded packages. Ro-Store independently rechecks
`Offline.get_status`, and only deletes its local safety journal when no
pending or staged update is reported. A failed request or ambiguous reply
preserves the journal and blocks new RPM mutations. Do not confuse this with
ordinary in-progress download cancellation.

**Required before release:** test staged download, explicit discard, recheck
after application restart, polkit refusal, and post-reboot journal recovery
on a disposable Fedora 44 installation or snapshot.

## v0.6 final handoff / acceptance (2026-10-16)

- Corrected DNF5 Offline D-Bus access: open `SessionManager.open_session` and call `Offline.get_status` on the returned session object, not on root. Use a separate short-lived read-only session and close it afterwards.
- Corrected Offline cleanup to `clean_with_options` on the session object; preserve the persistent safety journal if cleanup cannot be verified.
- Simplified the normal screen to package selection + `Güncelleme planını oluştur` + explicit `Güncelleme dosyalarını hazırla`; old `repoquery` dependency preview, download-only RPM cache tools, and read-only CLI offline status are in `Gelişmiş seçenekler`.
- CI (Fedora 44 x86_64 and aarch64) must show successful build and startup for the final commit, not an earlier commit.
- Live test 1: select two small, noncritical RPMs. Create the single DNF5 plan and check dependency list / removals without preparing or installing. Change selection and ensure the prior plan is invalidated; repeat.
- Live test 2: validate the new labels at 400×500, 600×500 and 1000×650, keyboard activation and scroll behavior; review status/error messages.
- Live test 3 (explicit separate approval only, ideally disposable VM/snapshot): review resolved update, validate no existing offline update, prepare the offline transaction, verify without reboot, discard and verify again. Reject admin authorization once; confirm safety journal persists on ambiguous result.
- Live test 4 (explicit separate approval only): reboot to apply an offline update; after reboot check `dnf5 offline log`, `dnf5 history`, recovery lock and journal workflow.
- Do not tag v0.6.0 or merge the PR until CI and all safety-critical live tests pass. Update CMake project version from 0.5.0 to 0.6.0 only as part of release preparation.
