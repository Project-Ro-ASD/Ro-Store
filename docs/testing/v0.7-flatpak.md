## Technical invariants

- Flatpak is a separate Qt/QML backend; no shell command execution. RPM/DNF5 remains unchanged.
- The scope (`--user` or `--system`) and exact app ID are passed as QProcess arguments, never shell strings.
- A valid scope, ID, remote, explicit UI confirmation and coordinator lock are required before mutation.
- A durable journal is written before mutation; an existing journal blocks further mutations.
- Mutations are not forcibly timed out. No silent cleanup of uncertain journal entries.
- Successful install/uninstall/Flathub remote-add only clears the journal after a successful **relevant scope-specific read** confirms the target state.
- App update baseline is captured with `flatpak info --show-commit` *before* the journal and process start. Successful update can clear its journal only when target read succeeds and installed commit differs. No runtime/extension updates through this path.
- Failed commands, unknown results and interrupted processes keep the journal for manual review.
- In-progress mutations and verification block forced exit, including tray Quit; safe background running may remain available.
- `Q_PROPERTY(inventoryRevision)` changes only after completed reads, so installed/launch labels react on the same page.
- User-scoped source addition uses official Flathub `.flatpakrepo`, preserving GPG verification.

## Operator acceptance commands (read-only)

```bash
flatpak --user remotes --columns=name,url
flatpak --user list --app --columns=application,name,version,origin
flatpak --user remote-ls --updates --columns=application,name,version,origin
find "${XDG_DATA_HOME:-$HOME/.local/share}" -name flatpak-transaction-journal.json -print
```

Inspect the app's transaction panel and log; do **not** delete journal files, remove system remotes or deliberately kill Flatpak on the primary workstation to satisfy remaining cases. Use an isolated disposable VM/user for fault injection.
