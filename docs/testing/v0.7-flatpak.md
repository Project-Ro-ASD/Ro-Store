# Ro-Store v0.7 — Flatpak / Flathub acceptance

## Release gate

**Limited-scope v0.7.0 release candidate.** The release permits only user-scoped Flathub remote addition and user-scoped Flathub app install/remove/launch. System-scope Flatpak mutations and all Flatpak updates are disabled in both the backend and UI. Full-function tests are deferred to the next roadmap milestone.

### Confirmed on Fedora 44 x86_64 (operator, 2026-10-21)

- User-scoped official Flathub remote added and verified using `flatpak --user remotes`.
- Installed `app.curocalc.calculator` 2.6.2 from Flathub, independently verified by `flatpak --user info`.
- Removed then reinstalled the same app, verified by `flatpak history --user`.
- Launched Curo Calculator; Flutter emitted shutdown warnings unrelated to Ro-Store's QML controls.
- Install/remove/launch buttons refresh without page navigation after the inventory revision fix.
- Transaction journal absent after final, confirmed operations.
- Fedora 44 CI built and tested x86_64 and aarch64 through commit `9dc2495`. Check later commits separately before release.

### Still unverified / must not silently infer success

- Genuine app update with a changed installed OSTree commit: no user-scope updates were available. **Do not update NVIDIA, runtimes, or drivers for this test.**
- Forced read failure, interrupted mutation, power loss or app crash, restart recovery.
- Authorization denied for system scope; multiple processes and simultaneous RPM/Flatpak locking.
- Disk full, offline network, inaccessible repo and corrupt journal.
- Automated tests of validation, journal lifecycle and fault injection.
- Full responsive/accessibility checks across specified resolutions and KDE themes.

## Technical invariants

- Flatpak is a separate Qt/QML backend; no shell command execution. RPM/DNF5 remains unchanged.
- The scope (`--user` or `--system`) and exact app ID are passed as QProcess arguments, never shell strings.
- A valid scope, ID, remote, explicit UI confirmation and coordinator lock are required before mutation.
- A durable journal is written before mutation; an existing journal blocks further mutations. The journal is rechecked under the cross-process lock to prevent overwriting a second instance's transaction.
- Mutations are not forcibly timed out. No silent cleanup of uncertain journal entries.
- Successful install/uninstall/Flathub remote-add only clears the journal after a successful **relevant scope-specific read** confirms the target state.
- All Flatpak updates are disabled in v0.7.0; update listings remain read-only. The commit-verification implementation remains for future testing but cannot be invoked by the UI or mutation API.
- Failed commands, unknown results and interrupted processes keep the journal for manual review.
- In-progress mutations and verification block forced exit, including tray Quit; safe background running may remain available.
- `Q_PROPERTY(inventoryRevision)` changes only after completed reads, so installed/launch labels react on the same page.
- User-scoped source addition uses official Flathub `.flatpakrepo`, preserving GPG verification.

## Operator acceptance commands (read-only)

```bash
flatpak --user remotes --columns=name,url
flatpak --user list --app --columns=application,name,version,origin
flatpak --user remote-ls --updates --columns=application,name,version,origin
find "${XDG_DATA_HOME:-$HOME/.local/share}" -name flatpak-transaction-journal.json -print
```

Inspect the app's transaction panel and log; do **not** delete journal files, remove system remotes or deliberately kill Flatpak on the primary workstation to satisfy remaining cases. Use an isolated disposable VM/user for fault injection.

## Deferred roadmap — full Flatpak support (v0.8+)

1. Disposable Fedora 44 VM: interrupt active install/uninstall; reboot and verify persistent journal recovery, failure diagnostics and non-corrupted Flatpak state.
2. Simulate network interruption, bad remote response, failed read, disk exhaustion and malformed journal; confirm fail-closed behavior, logs and recovery interface.
3. Validate denied Polkit authorization for system scope; verify cross-process Ro-Store and RPM/Flatpak lock contention under actual concurrent workloads.
4. With an actual application update available, verify old/new OSTree commit, download progress, failure and rollback handling; keep drivers, runtimes, codecs and extensions excluded until separately qualified.
5. Expand automated tests from source assertions to executable backend tests with mocked Flatpak processes and fault injection.
6. Validate full 400×500 / 600×500 / 1000×650 layout, scaling, keyboard control and KDE light/dark themes.
7. Only after these tests, consider enabling system-scope mutations, user-scope updates and unified RPM+Flatpak search in later releases.

No incomplete scenario above is claimed as validated for v0.7.0.
