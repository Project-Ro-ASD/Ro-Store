# Ro-Store v0.7 — Flatpak / Flathub integration acceptance

## Status

Experimental, **not release approved**. Never merge until CI and operator-verified Fedora 44 QA succeed. Existing v0.6 DNF5 paths are not intentionally modified.

## Architecture

- \`FlatpakManager\` is a separate Qt/C++ component using \`QProcess\` argv arrays, with no shell invocation.
- User vs system installations are explicitly separated; system operations may require host authorization.
- Read-only enumeration uses asynchronous commands, bounded output, timeouts, and no RPM mutations.
- Flatpak mutation requests validate identifier/scope/remote, require modal user confirmation, acquire \`PackageTransactionManager\`'s external operation lock, and persist an atomic journal **before** dispatch.
- Mutating processes are not subject to forced timeouts. Flatpak may internally require confirmation for permissions; \`--noninteractive\` is used to fail rather than hang.
- Journal lock stays after the command exits (even exit 0): the actual installed/depot state must be reviewed and the user must acknowledge recovery. Query failures prohibit journal acknowledgement until successful refresh. Error outcomes are treated as uncertain rather than success.
- The main window cannot be forced closed via the built-in “Yine de çık” button while an active Flatpak mutation is running.
- Single manager instance is owned by application window; page uses its reference. Existing RPM transaction manager is unchanged.

## Tests before merge

1. Fedora 44 x86_64: build; open Ro-Store home; navigate to Flatpak/Flathub; resize 400x500, 600x500, 1000x650. Ensure DNF5 existing flows still behave.
2. With Flatpak absent, show helpful error and leave DNF5 functional; with Flatpak present, refresh sources, installed apps and updates without mutation.
3. Check \`--user\` vs \`--system\` scope; verify correct commands and exact scope; test sources absent and multiple remotes. Verify catalog displays valid application IDs.
4. Reject invalid IDs/remotes, missing source, concurrent RPM transaction, journal present, and invalid confirmation.
5. On disposable test account first: install a small verified Flathub app, check journal lock, check updated installed list, inspect Flatpak CLI independently, recheck and acknowledge; run, update if available, and uninstall without \`--delete-data\`.
6. Deliberately deny authorization for a system-scope operation. Check that lock survives ambiguous result and that RPM queue cannot start while the operation is active. No silent success message.
7. Test corrupt/failed read, network disconnection, inaccessible repo, disk full, second instance, process crash, and restart recovery. In every ambiguous case require manual intervention.
8. CI Fedora 44 x86_64 and aarch64 build, RPM install and QML startup. Verify no QML binding/runtime errors. Add automated tests of argument validation/journal behavior before release.
9. Verify \`flatpak remote-ls --updates\` and \`--columns\` variants against Fedora 44 installed Flatpak version; correct incompatibilities before approving.
10. Verify security properties of Flatpak remote URLs and GPG signing; only manually reviewed official Flathub remote URL is offered by add-source action.

No v0.7.0 tag, release, or merge until these pass. Flatpak catalogs currently use text metadata, not rich screenshots; fully unified RPM/Flatpak search remains v0.8 scope.
